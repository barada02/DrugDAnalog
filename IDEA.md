# Analog — a molecule design workbench (WebMCP Challenge)

> Project spec. Developed separately from this repo — this repo is the WebMCP
> tryout/learning sandbox (see [readme.md](readme.md) for the API reference and gotchas).

**Working name:** *Analog* — in chemistry, an analog is a modified version of a
molecule, which is exactly what the app produces.

---

## 1. The pitch

A chemistry workbench where a human and their agent iterate on a molecule together,
and **every property claim is computed by RDKit rather than generated by the model.**

## 2. The core insight

Ask ChatGPT to improve a molecule today and it will confidently invent a logP value.
It cannot compute — it can only sound plausible. In a technical domain that is a real
and dangerous failure.

Here the app is the **referee**:

- The agent proposes
- RDKit computes
- The agent is **corrected by the tool** when it is wrong

That loop is the product. It is a structural answer to hallucination rather than a
disclaimer about it.

## 3. Why this needs WebMCP specifically

The filter that selected this idea: **can you paste the app's state into a chat box?**

You cannot paste a molecule. Before WebMCP, getting AI help meant photographing a
structure, describing it in prose, or building a brittle DOM-scraping agent. The model
had no access to computed truth and no way to act.

With WebMCP the user brings their own agent (ChatGPT's in-app browser, a Chrome
extension) and works alongside it inside the app. **The app provides capability; the
user brings intelligence.** No vendor lock-in to one model — the most *open web*
argument available.

## 4. Audience

| | |
|---|---|
| **Primary** | Chemistry and pharmacy students — large, accessible, acute pain |
| **Secondary** | Early-stage med-chem researchers doing analog exploration |
| **Tertiary** | Educators demonstrating structure–activity relationships live |

## 5. The collaboration loop

1. Load a starting molecule
2. State a goal in plain language — *"more water-soluble, keep the amide intact"*
3. Agent reads board state through tools
4. Agent proposes analogs as SMILES
5. **App computes real descriptors** — ground truth
6. Agent sees actual numbers and discards its own failures before showing you
7. You accept or reject the survivors
8. Accepted molecule becomes the new focus; lineage recorded
9. Repeat

**Three parties, none sufficient alone:** the agent knows med-chem heuristics and
enumerates tirelessly, the human knows what they are actually trying to make, and the
app is the only party that can compute truth.

## 6. Human-side features (must work with zero agent involvement)

Execution is a judging criterion — this has to be a complete product standalone.

- Load molecules via SMILES input or a preset library (aspirin, ibuprofen, caffeine, paracetamol…)
- 2D structure rendering (RDKit SVG — **verified working**)
- Live property panel: MW, logP, TPSA, HBD/HBA, rotatable bonds
- Lipinski / drug-likeness pass-fail with the specific violations named
- **Design board** of candidate cards
- **Lineage view** — what was derived from what; the design path is visible
- Side-by-side property comparison
- Mark a scaffold to preserve (substructure highlight)
- Per-candidate notes; export to CSV / SMILES

## 7. What the AI does

1. **Generates analogs** — bioisosteric replacements, functional-group swaps
2. **Explains structure–property relationships** using real computed numbers
3. **Screens its own proposals** — computes first, shows only survivors
4. **Reasons across multiple objectives** — *"more soluble, MW < 500, ring intact"*
5. **Explains failures** — which Lipinski rule broke and why
6. **Answers questions about the board** — *"which candidate has the best balance?"*

**Explicitly does NOT:** compute properties (RDKit does), decide (human does), or
change the focus molecule unilaterally (approval gate).

## 8. WebMCP tool surface

### Read tools
| Tool | Purpose |
|---|---|
| `get_workbench_state` | Focus molecule, board contents, active goal, constraints |
| `get_molecule_properties` | Full RDKit descriptors — **the ground-truth tool** |
| `check_substructure` | Does a candidate preserve the required scaffold? |
| `compare_molecules` | Property table across candidates |
| `get_design_goal` | What the human asked for |

### Write tools
| Tool | Purpose |
|---|---|
| `propose_candidate` | Add a card to the board (pending human approval) |
| `set_focus_molecule` | Change focus (approval gated) |
| `annotate_candidate` | Attach a note |
| `highlight_substructure` | Visually mark a scaffold on the canvas |
| `flag_violation` | Mark a rule break |

**The key design detail:** `propose_candidate` **returns the computed properties back
to the agent.** Propose something that makes logP worse and the tool says so
immediately. That is the self-correction loop, and it is the part most submissions
will not have.

Structural changes sit behind an **approval gate** — proposals land as pending cards.
Use the declarative-form pattern: omitting `toolautosubmit` turns human sign-off into
a product feature rather than a limitation.

## 9. Use cases

| Scenario | What happens |
|---|---|
| Student learns SAR | *"Why is ibuprofen more lipophilic than aspirin?"* — agent loads both, computes, explains with real numbers |
| Solubility optimization | *"More soluble, keep the amide"* — 5 proposed, 3 survive computation, human picks |
| Lipinski rescue | Compound violates two rules; agent iterates MW and logP down until it passes |
| Scaffold hopping | *"Keep this pharmacophore, change the core"* |
| Teaching demo | Instructor shows one functional-group change moving six properties at once |

### 3D — optional stretch goal

> ### ⚠️ Critical finding: RDKit's minimal WASM build is **2D only**
>
> Tested directly. After `set_new_coords()`, `has_coords()` returns `2` (meaning 2D)
> and **every z-coordinate is zero** — including when forcing `set_new_coords(true)`
> and `get_new_coords(true)`. The minimal build does not ship ETKDG conformer
> embedding.
>
> **3D coordinates must come from somewhere else.** Do not plan around RDKit for this.

#### Viewers (rendering only — all need coordinates supplied)

| Library | Version | Published | Notes |
|---|---|---|---|
| `3dmol` | **2.5.5** | May 2026 | Lightest, easiest. Can fetch PubChem directly: `$3Dmol.download('cid:2244', viewer)` |
| `ngl` | 2.4.0 | — | Scalable molecular graphics; heavier |
| `molstar` | 5.11.0 | — | Most powerful (used by RCSB PDB); heaviest, steepest learning curve |

**Recommendation: 3Dmol.js** — smallest, simplest, built-in PubChem fetching.
```
https://cdn.jsdelivr.net/npm/3dmol/build/3Dmol-min.js   (538 KB)
```

> **Verified by inspecting the bundle:** 3Dmol.js is a *viewer only*. It parses
> `sdf`, `mol2`, `pdb`, `xyz`, `cif`, `prmtop` — all formats that already contain
> coordinates — and has **zero** coordinate generation (no `generate3D`, `embed3d`,
> `conformer`, `ETKDG`, `minimize`, or force field). It renders coordinates; it never
> creates them.
>
> The 3D pipeline is therefore three stages, and 3Dmol only covers the last:
> ```
> SMILES  →  [coordinate source]  →  SDF  →  3Dmol renders
>            ^^^^^^^^^^^^^^^^^^^ the gap
> ```

**Practical strategy — use both sources:**

```js
// Presets / known compounds — built into 3Dmol, one line
$3Dmol.download('cid:2244', viewer, {}, () => viewer.render());

// Agent-generated novel analogs — CACTUS, arbitrary SMILES
const sdf = await fetch(cactusURL(smiles)).then(r => r.text());
viewer.addModel(sdf, 'sdf');
viewer.render();
```

PubChem covers the preset library (fast, reliable, trivial). CACTUS covers
agent-generated analogs, which by definition are not in PubChem. Fail gracefully:
if CACTUS is slow or down, the 2D view still works and nothing breaks.

#### Getting 3D coordinates — the actual problem

| Option | Works for | Trade-off |
|---|---|---|
| **NCI CACTUS resolver** ✅ *verified* | **Arbitrary SMILES** — including novel analogs | Network call; breaks the client-side privacy story; public service, no SLA |
| **PubChem PUG REST** | Known compounds only | Network; useless for agent-generated analogs |
| **Full RDKit WASM build w/ 3D** | Everything, offline | Must compile RDKit from source with conformer generation enabled — real effort |
| ~~`openbabel-wasm`~~ | — | **Does not exist on npm.** The `openbabel` package (1.2.3) is Node-only, not browser |

**CACTUS — verified working:**
```
https://cactus.nci.nih.gov/chemical/structure/{URL-encoded-SMILES}/file?format=sdf&get3d=true
```
Returned HTTP 200 with genuine 3D coordinates for aspirin (21 atoms, hydrogens added,
non-zero z values e.g. `0.0966, -0.2177, -1.3670`).

#### Recommended 3D strategy

Keep **2D as the default and fully client-side** — that preserves the privacy story
("your structures never leave your browser"), which is a genuine selling point for
pharma and impossible with a chatbot.

Make **3D explicitly opt-in**, with the network trade-off stated in the UI. This is
honest, keeps the core offline, and still gives you the 3D demo moment.

## 11. Scope control — what we are NOT building

Avoiding the "build the whole app, no time for WebMCP" trap:

- ❌ No structure-drawing editor — SMILES input + presets + agent generation
- ❌ No synthesis-route prediction
- ❌ No docking or binding-affinity prediction
- ❌ No backend, accounts, or database
- ⚠️ 3D viewing is a **stretch goal**, not core

**Fully client-side**, which buys three things:
1. Deploy free on any static host (Netlify, Vercel, Cloudflare, Render)
2. Zero server cost
3. A real privacy line — structures never leave the browser

## 12. Build order

1. **Core** — load molecule, render 2D, property panel
2. **Board** — candidate cards, lineage, comparison
3. **WebMCP imperative tools** — the read/write surface
4. **Approval gates** — declarative forms without `toolautosubmit`
5. **Polish** — presets, export, loading states
6. *(Stretch)* 3D via 3Dmol + CACTUS, opt-in

Riskiest item is the 6.9 MB WASM load, and it is a solved problem — a proper loading
state.

## 15. Testing notes

- **ChatGPT's in-app browser supports WebMCP with no flag** — easiest test path, and it is how judges will access the live URL
- Chrome: `chrome://flags/#enable-webmcp-testing` → Enabled → **Relaunch**
- WebMCP is `SecureContext`-only — `https://` or `http://localhost`, never `file://`
- It is **`document.modelContext`**, not `navigator.modelContext` (deprecated since Chromium 150)

Full API notes, both API styles, and the gotcha list are in [readme.md](readme.md).
